Database Joins:

Inner Join : returns matching records from both tables.

select * from employee e
INNER JOIN department d 
where d.department_id = e.department_id;

LEFT JOIN: returns all records from left and matching from right.

select * from from employee e
LEFT JOIN department data
where d.department_id = e.department_id;

RIGHT JOIN: returns all records from right and matching from left.

select * from from employee e
RIGHT JOIN department data
where d.department_id = e.department_id;

FULL JOIN :  returns all records from both tables.

selct * from employee e 
FULL JOIN department data
where d.department_id = e.department_id;

• CROSS JOIN: Produces a Cartesian product, combining every single row 
of the first table with every single row of the second table. 
If Table A has 10 rows and Table B has 10 rows, a CROSS JOIN yields 100 rows.
• SELF JOIN: Joins a table to itself. This is ideal for querying
 hierarchical structures stored in a single table, such as an Employees
 table where a column points to a manager_id inside the same table.

SQL NORMALIZATION

Definition:
Normalization is the process of organizing data in a database to reduce redundancy (duplicate data) and improve data integrity.

Advantages:
1. Eliminates duplicate data.
2. Improves data consistency.
3. Reduces storage usage.
4. Avoids Insert, Update, and Delete anomalies.
5. Makes database maintenance easier.

----------------------------------------------------
1NF (First Normal Form)
----------------------------------------------------

Rules:
1. Each column should contain atomic (single) values.
2. No repeating groups or multiple values in a single column.

Not in 1NF:

StudentId | StudentName | Subjects
------------------------------------
1         | Abhinav     | Java,SQL,Angular

After converting to 1NF:

StudentId | StudentName | Subject
----------------------------------
1         | Abhinav     | Java
1         | Abhinav     | SQL
1         | Abhinav     | Angular

----------------------------------------------------
2NF (Second Normal Form)
----------------------------------------------------

Rules:
1. Must be in 1NF.
2. Remove Partial Dependency.
3. Non-key attributes must depend on the complete primary key.

Example:

Student_Course

StudentId | CourseId | StudentName | CourseName
------------------------------------------------
1         | C101     | Abhinav     | Java
2         | C102     | Rohit       | SQL

Composite Key = (StudentId, CourseId)

Issues:
- StudentName depends only on StudentId.
- CourseName depends only on CourseId.

Convert to:

Student
--------
StudentId | StudentName
1         | Abhinav
2         | Rohit

Course
-------
CourseId | CourseName
C101     | Java
C102     | SQL

Enrollment
-----------
StudentId | CourseId
1         | C101
2         | C102

----------------------------------------------------
3NF (Third Normal Form)
----------------------------------------------------

Rules:
1. Must be in 2NF.
2. Remove Transitive Dependency.
3. Non-key attributes should depend only on the primary key.

Example:

Employee

EmpId | EmpName | DeptId | DeptName
------------------------------------
101   | John    | D1     | HR
102   | Smith   | D2     | IT

Issue:
EmpId -> DeptId
DeptId -> DeptName

DeptName indirectly depends on EmpId.

Convert to:

Employee
---------
EmpId | EmpName | DeptId
101   | John    | D1

Department
-----------
DeptId | DeptName
D1     | HR
D2     | IT

----------------------------------------------------
BCNF (Boyce-Codd Normal Form)
----------------------------------------------------

Rule:
Every determinant must be a candidate key.

Example:

Teacher | Subject | Room
-------------------------
T1      | Java    | R1
T2      | SQL     | R2

Dependencies:
Teacher -> Subject
Subject -> Room

Split into:

Teacher_Subject
---------------
Teacher | Subject
T1      | Java

Subject_Room
------------
Subject | Room
Java    | R1

----------------------------------------------------
4NF (Fourth Normal Form)
----------------------------------------------------

Rule:
Remove Multi-Valued Dependencies.

Example:

Student | Skill | Hobby
-------------------------
A       | Java  | Cricket
A       | SQL   | Cricket
A       | Java  | Music
A       | SQL   | Music

Convert to:

Student_Skill
-------------
A | Java
A | SQL

Student_Hobby
-------------
A | Cricket
A | Music

----------------------------------------------------
5NF (Fifth Normal Form)
----------------------------------------------------

Rule:
Remove Join Dependencies.

Used in complex databases where data is reconstructed through multiple joins.

Rarely used in real-world applications.

Windows Functions

Window Functions perform calculations across a set of rows related
to the current row without collapsing the result set (unlike GROUP BY).

1. ROW_NUMBER()
Assigns a unique number to each row.

SELECT name,
       salary,
       ROW_NUMBER() OVER (ORDER BY salary DESC) AS row_num
FROM employee;

2. RANK()
Gives same rank for ties and skips the next rank.

SELECT name,
       salary,
       RANK() OVER (ORDER BY salary DESC) AS rank_num
FROM employee;

3. DENSE_RANK()
Gives same rank for ties but does not skip ranks.

SELECT name,
       salary,
       DENSE_RANK() OVER (ORDER BY salary DESC) AS dense_rank
FROM employee;

4. NTILE()
Divides rows into groups.

SELECT name,
       salary,
       NTILE(2) OVER (ORDER BY salary DESC) AS bucket
FROM employee;

Output divides data into 2 equal groups


5. LAG()
Accesses previous row value.

SELECT name,
       salary,
       LAG(salary) OVER (ORDER BY salary) AS previous_salary
FROM employee;

6. LEAD()
Accesses next row value.

SELECT name,
       salary,
       LEAD(salary) OVER (ORDER BY salary) AS next_salary
FROM employee;


SQL Views

A View is a virtual table created from one or more tables using a SQL query.

It does not store data physically (except Materialized Views).
It stores the SQL query.
Whenever you query the view, data is fetched from the underlying tables.

CREATE VIEW view_name AS
SELECT column1, column2
FROM table_name
WHERE condition;

SQL TRIGGERS - INTERVIEW NOTES
=========================

1. WHAT IS A TRIGGER?
--------------------
A Trigger is a special stored procedure that automatically executes when an event
(INSERT, UPDATE, DELETE) occurs on a table or view.

Uses:
- Auditing changes
- Data validation
- Maintaining history tables
- Enforcing business rules
- Updating related tables automatically

--------------------------------------------------

2. TYPES OF TRIGGERS
--------------------

A. BEFORE TRIGGER
   Executes before INSERT, UPDATE, or DELETE.

B. AFTER TRIGGER
   Executes after INSERT, UPDATE, or DELETE.

--------------------------------------------------

3. BEFORE INSERT TRIGGER EXAMPLE
--------------------------------

CREATE TRIGGER trg_check_salary
BEFORE INSERT ON employee
FOR EACH ROW
BEGIN
    IF NEW.salary < 0 THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Salary cannot be negative';
    END IF;
END;

Usage:

INSERT INTO employee(id, name, salary)
VALUES (1, 'John', -5000);

Output:
Error: Salary cannot be negative

--------------------------------------------------

4. AFTER INSERT TRIGGER EXAMPLE
-------------------------------

Employee Table:

CREATE TABLE employee (
    id INT,
    name VARCHAR(50),
    salary DECIMAL(10,2)
);

Audit Table:

CREATE TABLE employee_audit (
    emp_id INT,
    action_type VARCHAR(20),
    action_time TIMESTAMP
);

Trigger:

CREATE TRIGGER trg_after_insert_emp
AFTER INSERT ON employee
FOR EACH ROW
BEGIN
    INSERT INTO employee_audit
    VALUES (NEW.id, 'INSERT', NOW());
END;

Insert:

INSERT INTO employee
VALUES (1, 'John', 50000);

Audit Table Entry:

1 | INSERT | 2026-10-19 12:00:00

--------------------------------------------------

5. INSERT TRIGGER
-----------------

CREATE TRIGGER trg_insert
AFTER INSERT ON employee
FOR EACH ROW
BEGIN
    INSERT INTO log_table(msg)
    VALUES(CONCAT('Employee Added : ', NEW.name));
END;

NEW Keyword:
------------
NEW.id
NEW.name
NEW.salary

Represents the newly inserted row.

--------------------------------------------------

6. UPDATE TRIGGER
-----------------

CREATE TRIGGER trg_update_salary
AFTER UPDATE ON employee
FOR EACH ROW
BEGIN
    INSERT INTO employee_audit
    VALUES(
        NEW.id,
        CONCAT(
            'Salary changed from ',
            OLD.salary,
            ' to ',
            NEW.salary
        ),
        NOW()
    );
END;

Update:

UPDATE employee
SET salary = 60000
WHERE id = 1;

OLD.salary = 50000
NEW.salary = 60000

OLD -> Value before update
NEW -> Value after update

--------------------------------------------------

7. DELETE TRIGGER
-----------------

CREATE TRIGGER trg_delete_emp
AFTER DELETE ON employee
FOR EACH ROW
BEGIN
    INSERT INTO employee_audit
    VALUES(OLD.id, 'DELETE', NOW());
END;

Delete:

DELETE FROM employee
WHERE id = 1;

Audit Table Entry:

1 | DELETE | 2026-10-19 12:30:00

--------------------------------------------------

8. OLD VS NEW
-------------

OLD:
- Available in UPDATE and DELETE triggers.
- Represents data before modification.

NEW:
- Available in INSERT and UPDATE triggers.
- Represents data after modification.

Example:

UPDATE employee
SET salary = 70000
WHERE id = 1;

OLD.salary = 60000
NEW.salary = 70000

--------------------------------------------------

9. TRIGGER VS STORED PROCEDURE
------------------------------

Trigger:
- Executes automatically.
- Event-driven.
- Cannot be called directly.
- Associated with a table/view.

Stored Procedure:
- Executed manually.
- User/Application driven.
- Can be called using CALL statement.
- Independent database object.

--------------------------------------------------

10. CASCADING TRIGGERS
----------------------

One trigger causes another trigger to execute.

Example:
Trigger on Table A inserts data into Table B.
Table B has another trigger.
Both get executed automatically.

--------------------------------------------------

11. DISADVANTAGES OF TRIGGERS
-----------------------------

- Hidden business logic.
- Can impact performance.
- Hard to debug.
- May lead to recursive/cascading execution.
- Increased maintenance complexity.

--------------------------------------------------

-----------------------------

Orders Table:

orders
